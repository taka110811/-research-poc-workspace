# PoC Design

## Goal

Validate whether the existing reproduction code can demonstrate Byzantine-resilient distributed optimization on a small synthetic linear regression problem.

## Research Question

Can data encoding and real-number error correction recover correct distributed computation results when up to `t` workers return Byzantine responses?

## Hypothesis

For small synthetic datasets, the encoded matrix-vector multiplication can recover useful results under injected worker corruption, and the runtime overhead can be measured across different values of `t`.

## Background

The seed paper proposes encoding worker data and decoding corrupted worker responses using error correction over real numbers. The current implementation focuses on GD and CD for linear regression and simulates Byzantine workers with additive noise.

## Scope

### In Scope

- Synthetic linear regression
- Simulated workers
- GD and CD one-iteration timing
- Attack count sweep over `t`
- Runtime and recovery-oriented metrics

### Out of Scope

- Production distributed execution
- Full paper reproduction
- Real datasets
- Comparison against many robust aggregation baselines

## Success Criteria

- The experiment runs from a documented command.
- Results are recorded under `poc/runs/<date>/`.
- The report explains whether the output supports continuing the research.
- The decision memo states Continue, Pivot, or Stop.

## Failure Criteria

- The implementation cannot run locally.
- The output is not interpretable enough to guide a decision.
- The PoC requires a scope larger than local experimentation.

## Baseline

The initial baseline is no Byzantine corruption or the lowest supported attack count. A stronger future baseline would compare against plain distributed GD/CD without encoding.

## Method

Run `src/experiment.py`, capture the command, parameters, runtime table, and any observed failure modes. If needed, adjust the script only enough to make outputs reproducible and easy to record.

## Risks

- Numerical instability in syndrome decoding or linear programming.
- Runtime may be dominated by the Python/SciPy implementation rather than the algorithmic idea.
- The current script may need additional logging for clean PoC reporting.

## Decision Rule

Continue if the experiment runs, produces interpretable `t`-sweep results, and the implementation gaps are clear enough to address. Pivot if the current implementation is too approximate but the research question remains useful. Stop if the PoC cannot produce interpretable evidence locally.
